# Deploying FRACTAL on Render

The repository ships a [Render Blueprint](../render.yaml) that creates
everything FRACTAL needs: Postgres, the Go API (with the OPA policy engine
embedded), the merchant store, the investigator, and the static web UI.

After deployment there is **no cloudflared tunnel**. The API and store derive
their public origin from Render's stable `RENDER_EXTERNAL_URL`, so PayPal
webhook URLs and checkout return URLs survive restarts and redeploys.

## What gets created

| Resource | Type | Public | Notes |
|---|---|---|---|
| `fractal-postgres` | Postgres 16 | private | Stores cases, payments, webhooks, audit data |
| `fractal-api` | Docker web service | yes | Runs migrations, embedded OPA, API on `$PORT` |
| `fractal-store` | Docker web service | yes | Demo merchant checkout + webhook receiver |
| `fractal-investigator` | Docker web service | yes | Advisory AI agent, token-protected |
| `fractal-web` | Static site | yes | React UI, built with `VITE_API_BASE` pointing at the API |

The API image contains the `/opa` binary and the policies from `policies/`, so
there is no separate OPA service. Locally, docker compose still uses the
dedicated `opa` service (`OPA_URL=http://opa:8181`).

## Public URL resolution

This is the part that replaces the tunnel:

| Service | Order used to build public URLs |
|---|---|
| API | `FRACTAL_PUBLIC_URL` → `PUBLIC_TUNNEL_URL` → `RENDER_EXTERNAL_URL` → request headers |
| Merchant store | `MERCHANT_PUBLIC_URL` → `RENDER_EXTERNAL_URL` → `http://localhost:8090` |

The blueprint sets `FRACTAL_PUBLIC_URL` and `MERCHANT_PUBLIC_URL` from each
service's own `RENDER_EXTERNAL_URL`. `PUBLIC_TUNNEL_URL` remains supported for
local tunnel development and is ignored on Render.

## 1. Push the repository

Render deploys from GitHub/GitLab. Push this branch (the blueprint and Docker
changes must be included):

```bash
git push origin <branch>
```

## 2. Create the Blueprint

1. In Render, choose **New → Blueprint**.
2. Select the repository and branch.
3. Render previews the five resources above. Apply the Blueprint.

### Values to enter

The blueprint asks for values marked `sync: false`. Copy them from your local
`.env` — do not commit them, and do not paste them into chat or logs.

| Variable | Where to find it |
|---|---|
| `PAYPAL_CLIENT_ID` | `PAYPAL_CLIENT_ID` in `.env` (PayPal Developer → your Sandbox app) |
| `PAYPAL_CLIENT_SECRET` | `PAYPAL_CLIENT_SECRET` in `.env` |
| `PAYPAL_WEBHOOK_ID` | `PAYPAL_WEBHOOK_ID` in `.env`, or the webhook ID in the PayPal Developer Dashboard. Can be updated after re-registration. |

`PAYPAL_BASE_URL` defaults to `https://api-m.sandbox.paypal.com`.
`FRACTAL_JWT_SECRET`, `FRACTAL_ENCRYPTION_KEY`,
`MERCHANT_INTEGRATION_SECRET` and `INVESTIGATOR_TOKEN` are generated by Render
and persist across deploys.

The blueprints keeps Postgres private (`ipAllowList: []`). If you need to
connect from your laptop for the demo-data import below, add your IP under
**fractal-postgres → Access Control** temporarily.

## 3. Verify the first deploy

Render's health checks use:

- API: `/healthz` → `{"status":"ok"}`
- Store: `/` → storefront HTML
- Investigator: `/healthz`

Copy the API's public URL from the dashboard (for example
`https://fractal-api.onrender.com`) and check:

```bash
curl -fsS "$API_URL/healthz"
curl -fsS "$API_URL/api/v1/onboarding/regions"
```

Open the static site URL. The UI should load and talk to the API directly
(`VITE_API_BASE` was baked in at build time).

Free services spin down after about 15 minutes of inactivity. The first request
after that can take 30–60 seconds. The web static site never spins down.

## 4. Point PayPal at the stable URL

The old registrations still point at the `trycloudflare.com` tunnel, so they
must be moved to the Render URL once.

### Per-merchant account (including the Google demo merchant)

The merchant's webhook registration is stored in `provider_accounts`. The
recovery path also handles a changed public URL:

1. Sign in to the UI as the merchant owner.
2. Open the **PayPal setup** page for the merchant and choose **Re-register
   webhook** (or call the endpoint with the merchant's token):

```bash
curl -fsS -X POST "$API_URL/api/v1/onboarding/paypal/re-register" \
  -H "Authorization: Bearer $MERCHANT_TOKEN"
```

The endpoint derives the new URL from `FRACTAL_PUBLIC_URL` and PATCHes the
existing PayPal webhook in place. Confirm with:

```sql
SELECT webhook_id, webhook_url, webhook_status
FROM provider_accounts
WHERE merchant_id = 'dd360069-ca76-431b-94e5-277c47dcfffc';
```

`webhook_url` must be `https://<fractal-api-host>/api/v1/webhooks/paypal/<account-id>`.

### Legacy/deployment-level demo account

`scripts/paypal_webhook.py` updates the webhook whose ID is in
`PAYPAL_WEBHOOK_ID`. Set `FRACTAL_PUBLIC_URL` (it now also accepts this instead
of `PUBLIC_TUNNEL_URL`) and run it:

```bash
FRACTAL_PUBLIC_URL="$API_URL" make webhook-sync
```

If PayPal reports the 10-webhook sandbox limit, delete unused webhooks in the
PayPal Developer Dashboard first.

## 5. Optional: import the local demo data

The incident demo (`INC-5073`, `FR-10xxx`, the Google merchant) lives in the
local database. Import it after the first successful deploy and **before**
creating merchants through the deployed UI, so seeded emails do not conflict.

```bash
# 1. Dump data only; keep the Render schema and migration ledger.
pg_dump "$LOCAL_DATABASE_URL" \
  --data-only --no-owner --no-privileges \
  --exclude-table=schema_migrations \
  -f /tmp/fractal-demo.sql

# 2. Temporarily allow your IP on fractal-postgres, then import.
psql "$RENDER_EXTERNAL_DATABASE_URL" -f /tmp/fractal-demo.sql

# 3. Remove the access rule from fractal-postgres.
```

Then re-register the merchant webhook as in step 4 (the imported row still has
the tunnel URL) and restart the API so cached credentials are re-read.

### Sign in to the imported demo

Seeded demo users have no password hash; they normally use the local dev-login
shortcut. That shortcut is disabled on Render (`FRACTAL_DEV_LOGIN_ENABLED=false`)
so nobody can impersonate an account by knowing its email. Set a password for
the accounts you need:

```bash
# Option A: Render Shell for fractal-api (if available on your plan)
/bin/setpassword owner@example.com 'choose-a-long-password'

# Option B: from your machine, with your IP temporarily allowed on Postgres
DATABASE_URL="$RENDER_EXTERNAL_DATABASE_URL" \
  make set-password EMAIL=owner@example.com PASSWORD='choose-a-long-password'
```

Use the normal email + password form on the login page. Leave the password field
empty only in local development, where the role switcher uses dev-login.

Secrets in the dump are encrypted with your local
`FRACTAL_ENCRYPTION_KEY`. For the demo merchant this is irrelevant: it uses the
platform PayPal app, which reads `PAYPAL_CLIENT_ID`/`PAYPAL_CLIENT_SECRET` from
the Render environment. If you imported a merchant that stored its own PayPal
secret, re-enter it through the UI — the Render key is different by design.

## Free-tier limits to know

- Web services sleep after ~15 minutes idle. PayPal retries failed webhook
  deliveries, but a cold start can add latency. Upgrade the API service to the
  cheapest paid instance if webhook latency matters.
- Free Postgres has no persistent disk and Render deletes free databases after
  the free period (30 days). Export data before it expires.
- The store keeps orders in `MERCHANT_STORE_PATH` (`/app/orders.json`), which is
  ephemeral on free instances. Captured payments, webhooks, cases and claim
  tokens are in Postgres and survive restarts. For durable store orders, use a
  paid instance with a disk mounted at `/data` and set
  `MERCHANT_STORE_PATH=/data/orders.json`.
- Free services share CPU. The investigator is optional; without `LLM_API_KEY`
  it uses its deterministic fallback and still returns a verified advisory.

## Environment variables reference

Required on the API:

| Variable | Source |
|---|---|
| `DATABASE_URL` | Blueprint (`fromDatabase`) |
| `FRACTAL_PUBLIC_URL` | Blueprint (self-referenced `RENDER_EXTERNAL_URL`) |
| `FRACTAL_JWT_SECRET` | Generated by Render |
| `FRACTAL_ENCRYPTION_KEY` | Generated by Render (seals merchant PayPal secrets) |
| `PAYPAL_CLIENT_ID`, `PAYPAL_CLIENT_SECRET` | Dashboard (`fractal-paypal` group) |
| `PAYPAL_BASE_URL` | Blueprint value |
| `PAYPAL_WEBHOOK_ID` | Dashboard |
| `MERCHANT_INTEGRATION_SECRET` | Generated, shared with the store |
| `INVESTIGATOR_TOKEN` | Generated, shared with the investigator |
| `MERCHANT_STORE_BASE` | Blueprint (`hostport`, scheme added in code) |
| `INVESTIGATOR_URL` | Blueprint (`hostport`, scheme added in code) |
| `OPA_URL` | Omit on Render; the entrypoint starts embedded OPA |

Optional: `FRACTAL_ANOMALY_ENABLED` (default `false`), `KIBANA_URL`,
`OTEL_ENDPOINT`, `LLM_API_KEY` (set on the investigator only).

`FRACTAL_DEV_LOGIN_ENABLED` is `false` on Render and `true` in
`docker-compose.yml`. Never enable it on an instance reachable by untrusted
users: it issues tokens for passwordless seeded accounts without a password.

## Troubleshooting

**Migrations.** The API entrypoint runs `/bin/migrate` on every boot. It holds a
Postgres advisory lock, records versions in `schema_migrations`, and baselines a
database that already has the old schema but no ledger. If a migration fails,
the API refuses to start and the Render logs show the failing version.

**CORS.** The API reflects the request `Origin`, so the static site can call it
cross-origin. If you put a custom domain in front of the API, update
`FRACTAL_PUBLIC_URL`/`VITE_API_BASE` and redeploy the static site so the bundle
is rebuilt.

**PayPal signature failures.** A webhook URL registered against a different
origin (the old tunnel) fails signature verification. Re-register as in step 4
and confirm the URL in `provider_accounts`.

**Build cache.** `VITE_API_BASE` is a build-time value. Changing the API URL
requires a new static-site deploy, not just a restart.

**Cannot sign in to a deployed demo.** The role switcher uses the dev-login
endpoint, which is disabled on Render. Set a password for the account (see
step 5) and use the email/password form.
